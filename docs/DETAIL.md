# 梯子开关

需要访问无法直连的网络时，把本实例的出网请求切到本地代理；平时保持直连。

**不用配端口。** 插件会自己在本机找代理：Clash Verge、v2rayN、sing-box、Shadowsocks 用哪个客户端、开在哪个端口，都能直接用。

## 为什么需要它

DSH 只在**启动时**读一次 `HTTP_PROXY` / `HTTPS_PROXY`。这带来两个尴尬：

- 启动时代理客户端没开，这个进程就一直是直连，想翻墙只能重启
- 把代理写死在环境变量里，客户端没开时所有请求指向空端口，DSH 直接瘫痪

本插件在运行中替换 undici 的全局 dispatcher，于是两种状态随时可切。

## 四个工具

| 工具 | 作用 |
|---|---|
| `proxy_on` | 自动找到本机代理端口，通了就装上并立即生效；找不到则如实报告并保持直连 |
| `proxy_off` | 卸掉代理，恢复直连，立即生效 |
| `proxy_status` | 只读查询：现在走不走代理、用的是哪个端口、端口通不通 |
| `proxy_detect` | 只读查询：列出本机探测到的所有代理端口，以及每个端口为什么可用或不可用 |

## 自动探测端口

不同代理软件的默认端口并不一样，把某一个写死就等于让其他人装完即失效。插件因此按下面的顺序自己找：

1. **环境变量** — 你导出的 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY`
2. **Windows 系统代理** — 客户端自己发布到注册表的地址
3. **常见客户端默认端口** — Clash Verge 7897、v2rayN 10809、mihomo 7890、sing-box 2080、v2rayA 20170 等十五种

**探测只在插件加载时做一次**，结果缓存到本进程结束。之后每次「开代理 / 关代理」都直接用缓存结果，不会再扫一遍端口——反复遍历本机端口正是安全软件判定端口扫描的行为，插件不该有那个样子。

`proxy_status` 会显示「本次已探测 N/3 次」，正常情况下恒为 `1/3`，可以自查。整个进程最多探测 3 次（加载 1 次 + 换客户端时机 2 次），不会因为你反复点「开代理」就反复探测。

**探测结果只存在内存里，不会写回你的配置文件。** 说「开代理」时就用这个结果直接装上，不需要你手动填端口。

两种情况会自动重探，都**不做全端口扫描**：

1. **加载时什么都没找到**（比如先开了 DSH、后开客户端）——下次开代理时重探一次
2. **缓存的端口已经不通**（换了代理客户端，或客户端关过）——重探到新端口

第 2 条很重要：如果只信加载时的缓存，换了客户端之后插件会一直报「找不到」，哪怕新客户端跑得好好的。

**但装之前一定会确认端口是通的。** 缓存只是「上次看到它在哪」的提示，不是承诺。装上一个死端口会让本实例每个请求都 `ECONNREFUSED`，那正是这个插件要防的事。所以 `proxy_on` 在安装前会做**一次**回环连接确认（只连这一个已知端口，不枚举任何东西）。通了才装，不通就如实说「客户端可能已退出」并保持直连。

### 可选：扫描全部监听端口

如果你的客户端改到了非常见的端口，前三步都找不到，可以显式开启全端口扫描：

```yaml
- id: tizi-switch
  config:
    scanListeningPorts: true
```

默认**关闭**：全端口扫描更容易触发安全软件告警，而常见端口已经覆盖了绝大多数人。

开启后**整个进程生命周期最多扫一次**（就是加载时那次），后续重探只读环境变量、系统代理和那 15 个常见端口。`proxy_status` 会显示「已用过一次全端口扫描」。

### 怎么判断一个端口「真的是代理」

端口能连上**不等于**它是代理。DSH 自己的 Web 界面、开发服务器、本地数据库都接受连接，把 dispatcher 指过去会让每个请求都失败。

所以插件发一个 HTTP `CONNECT` 握手：这是 HTTP 代理必须实现的协议，普通 Web 服务不会正确应答。只有应答了才认定为可用代理。

探测请求的目标固定为 `127.0.0.1:9`（一个没有服务的丢弃端口），因此**握手不会真的建立隧道**，探测过程不会向你当前的代理节点发送任何流量。

### SOCKS 端口会被识别但不使用

DSH 只支持 `http://` / `https://` 代理。若只找到 SOCKS 端口（v2rayN 的 10808、v2rayA 的 20171 等），插件会明确告诉你「这是 SOCKS 端口，请在客户端里再开一个 HTTP / mixed 入站」，而不是假装成功。

## 自动回退：代理客户端退出后不再断网

代理装上后，本实例的**所有**请求都指向那个端口。如果代理客户端被关掉，端口无人应答，每个请求会以 `ECONNREFUSED` 立刻失败——从使用者角度看就是"网断了"。

插件因此每 3 秒探测一次端口，发现不通就自动卸掉代理、回到直连。实测数据：

| 阶段 | 结果 |
|---|---|
| 装代理后请求 | HTTP 200 |
| 关掉代理端口 | `ECONNREFUSED`（约 2ms） |
| 健康检查触发（≤3s） | 自动回退到直连 |
| 回退后请求 | HTTP 200 |

**为什么回退后不自动重新开启**：代理客户端的端口在启动阶段可能反复抖动，自动恢复会让路由来回切换，状态变得不可预期。所以发现端口消失就退回直连并停止探测，客户端重新就绪后由使用者说一句「开代理」即可。

**为什么用轮询而不是"请求失败时回退"**：undici 的全局 dispatcher 是同步解析的，一次请求失败后无法在同一个请求里换路由。轮询是唯一能在客户端消失后主动恢复的方式。回环连接要么立刻成功要么立刻被拒，所以探测成本可以忽略，并且定时器 `unref()`，不会吊住进程。

关闭自动检测：`healthCheckMs: 0`。

## 配置

**默认无需配置**，开箱即用。

手动指定端口（跳过自动探测）：

```yaml
- id: tizi-switch
  config:
    port: 7897
```

配置了端口后仍会校验它——指向死端口会拒绝安装并保持直连，不会把 DSH 弄瘫。

其余可选项：

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `host` | `127.0.0.1` | 代理主机；探测与安装都用这个地址 |
| `port` | 不设=自动探测 | 指定端口则跳过自动探测 |
| `probeTimeoutMs` | `400` | 单个端口探测超时（毫秒） |
| `healthCheckMs` | `3000` | 对已启用端口的健康检查间隔；`0` 关闭 |
| `scanListeningPorts` | `false` | 是否扫描全部监听端口（可能触发安全软件告警） |
| `reportLimit` | `5` | `proxy_status` 里最多显示几个探测到的端口 |

## 边界

- **不读写操作系统代理设置**，只改本进程内的 dispatcher
- **不影响其他软件**，浏览器照常
- **只作用于本进程**：模型调用、`web_fetch`、`web_search`、HTTP MCP
- 不覆盖模型自己写的脚本子进程、以及使用 `node:http` 的遥测通道（上游既定边界）
- 不支持需要用户名口令的代理（会识别并报告，但不会安装）

## 关键实现细节

**切换前先验证端口**：指向死端口会快速 `ECONNREFUSED`。无脑装代理等于把「忘了开客户端」变成「DSH 瘫掉」。所以 `proxy_on` 先做 HTTP 握手验证，探不到就拒绝且不改动当前路由。

**`proxy_off` 不等 dispose 完成**：`dispose()` 尾部的 `agent.close()` 要等在途连接结束，可能几十秒；但头部还原 dispatcher 是同步的，路由早已切回。等待整个 dispose 只会让调用看起来卡死。

**为什么用动态导入**：本地 link 安装时，profile 的 `node_modules` 解析不到 `@deepseek-ai/*`，所以要经 `DSH_INSTALL_DIR` 用 `file://` URL 导入。

**探测不依赖第三方库**：全部用 `node:net` 的裸 TCP 实现，插件保持零外部依赖。
